Guarantees

G1

Same result on every runtime. Same output and same error type for every input, including engines without native hex, TextEncoder/TextDecoder or isWellFormed.

G2

Strict decoding. A string decoder accepts only the strings its encoder can produce. Everything else throws a TypeError. Nothing is silently replaced, dropped or ignored.

G3

Exact round trips. Every encoding is 1:1, except the cases listed under each format (letter case in hex and uvy, bigint trailing zeros).

G4

Inputs are never modified.

G5

Argument types are not checked. A wrong type is undefined behaviour: any error, or garbage. Only string content is validated.

E1, E2, E5, E6 and E7 throw a SyntaxError, as native fromHex does. E3 and E4 throw a TypeError, as a fatal TextDecoder does. No rethrow.

hex

H1 Output: 2 lower case chars per byte, high nibble first, no prefix or separators.

H2 Input: an even-length string of 0-9 a-f A-F. "" gives an empty array.

H3 Upper case is accepted, as native fromHex does. So hex is not 1:1: "AB" and "ab" both give [0xab]. See D1.

utf8

U1 Encoding: the string must be well-formed UTF-16. No BOM is added.

U2 Decoding: the bytes must be valid UTF-8 (fatal decoder).

U3 A leading BOM EF BB BF is kept as "﻿", not stripped. The default TextDecoder strips it, which breaks 1:1. See D2.

U4 For lossy conversion, use s.toWellFormed() or your own non-fatal decoder.

uvy

V1 Alphabet 0123456789abcdefghijklmnoprstuvy. The first 16 digits are the hex digits.

V2 Bitstream, MSB first, 5 bits per char, the last char padded with 0 bits, no padding chars. 5 bytes ↔ 8 chars.

V3 ceil(n*8/5) chars for n bytes. Output is lower case. Input may also be upper case (as in hex).

V4 "00" gives [0]. "01", "02" and "03" throw. 1:1 apart from letter case. Padding position: see D6.

bigint

B1 Unsigned little-endian. Empty in, 0n out.

B2 Not 1:1, and there is no inverse: [1], [1,0] and [1,0,0] all give 1n. See D4.

Shared memory pool

P1 hexToBytes, utf8ToBytes and uvyToBytes return results of 4 KB or less as views into a shared block. Larger results get their own buffer. D3

P2 Use the Uint8Array, never its .buffer. Don't assume byteOffset is 0.

P3 .slice() gives you your own copy. Transferring .buffer detaches every other result in the same block.

P4 The library never writes to a returned result again. Writing to your result changes only your result.

P5 A small result you keep alive keeps its whole block alive (up to 8 KB).

P6 Pool results start at a byteOffset that is a multiple of 8.

Decided

  • D1 hex accepts upper case. uvy accepts upper case too (from your E6 note). Both are documented as the only case exception to 1:1.
  • D2 ignoreBOM: true: a leading BOM is kept.
  • D3 The README states exact pool numbers. Answer on the pool size: no, it was never measured. 8 KB was copied from Node's Buffer, and the benchmarks only compared pool vs. no pool. Point 5 now benchmarks 2, 4, 8 and 16 KB blocks.
  • D5 Errors follow the platform, no rethrow: hex and uvy throw SyntaxError, utf8 throws TypeError.
  • D7 Deferred: little-endian stays. uvyToBigInt waits until there is a real need.
  • D4 Document only. uvyToBigInt/bigIntToUvy and uvyToHex/hexToUvy went to deferred.md.

Open decision

D6 - uvy: full 8-char blocks only? verify performance first: sub-task 4

Answer to your question: a block loop (5 bytes ↔ 8 chars with fixed shifts) is very likely faster than today's bit-by-bit accumulator. But partial blocks can use the same block loop and handle only the last (or first) block separately, which is one extra step per call. So I expect full-block-only to give no real speed gain. That is now a benchmark in sub-task 4, to run before deciding.

The catch: full 8-char blocks only means the byte length must be a multiple of 5. A 16-, 32- or 64-byte key or hash could not be encoded (32 % 5 = 2). Inside a full block, the order is already analogous to hex: 40 bits, most significant first.

1:1 is easy in every option: one comparison per call, on the char that holds the padding bits. So the real choice is where a partial block's padding goes:

PaddingMeaning of the string[0xff] →
Aat the end (RFC 4648, as today)a bitstream"yt"
Bat the frontthe big-endian number in base 32, exactly as hex is the number in base 16"7y" (= 255)
Cnone allowedblocks only; bytes must be a multiple of 5throws

A and B cost the same and only differ for lengths that are not a multiple of 5. B is the closest analogue to hex, and it makes bigIntToUvy nearly free: n.toString(32) plus a char map (native base 32 uses q/w/x, we skip them).
